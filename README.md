# Kid Icarus: Uprising

Matching reconstruction of **Kid Icarus: Uprising** for Nintendo 3DS.

This tree targets the Japanese Rev 1 retail build. It contains source
reconstructions for functions with a recorded high byte-match score, the
decompressed retail code image used as the target.

## Target and scope

- **Game:** Kid Icarus: Uprising
- **Platform:** Nintendo 3DS
- **Target:** JP Rev 1
- **SDK context:** CTR SDK 3.2.5.200
- **Primary matching compiler:** ARM Compiler 4.1
- **Target image:** `target/jp_rev1/code.bin`
- **Function inventory:** `data/functions.tsv`
- **Defined-data inventory:** `data/data.tsv`

`code.bin` is the decompressed ExeFS code image, not a ROM or game
container. The repository does not include game assets, a ROM, or a complete
retail build environment. You must obtain any game data and proprietary
compiler/SDK components lawfully.

The inventory contains 24,890 functions and 125,176 `DAT_` labels. Defined
data is measured separately: `data/data.tsv` contains 164,072 unique Ghidra
data objects totaling 925,843 bytes. Multiple labels can refer to one data
object, so label counts and byte totals are intentionally different.

ARM Compiler 4.1 is currently the primary byte-matching reference because it
is the available ARMCC toolchain closest to the retained target environment.
The target compiler/profile is still an active research question; scores are
therefore reported with their compiler provenance rather than presented as
unqualified correctness claims. Every reconstructed function is suffixed with
its retail address to keep source names stable and traceable.

## Dependencies

For the included metadata and report scripts:

- Git
- Python 3.9 or newer
- `objdiff-cli` when validating reports or comparing object files

To reproduce ARM byte matching, you additionally need the matching ARM
Compiler 4.1 toolchain, the appropriate CTR SDK 3.2.5.200 headers/libraries,
ARM binutils, and the JP Rev 1 target image. Those components are not
distributed here.

## Building

This snapshot does not yet contain a whole-game linker configuration or
reproducible top-level build command. The files under `src/` are source
reconstructions, while `include/` contains shared views which were recognized
to be constantly reused/referenced in functions.

When the target-specific build configuration is available, the expected build
flow is:

1. Compile each reconstruction with the ARMCC 4.1 target flags.
2. Link or extract the resulting object/function using the JP Rev 1 address
   and section layout.
3. Compare the generated bytes with the corresponding span in
   `target/jp_rev1/code.bin`.

Do not use a host compiler score as evidence of an ARMCC match. GCC or another
host compiler is useful only for syntax and semantic checks.

## Diffing and reports

Generate the decomp.dev-compatible progress report locally:

```sh
python3 scripts/generate_decomp_report.py \
  --catalog data/functions.tsv \
  --data data/data.tsv \
  --output build/report.json
```

The GitHub Actions workflow generates the same report on every push and
uploads it as the `jp_rev1_report` artifact.

For object-level comparison, use objdiff directly once you have a built base
object and its retail target object:

```sh
objdiff-cli diff \
  --target path/to/retail.o \
  --base path/to/reconstruction.o \
  --format json \
  --output build/function-diff.json \
  SYMBOL_NAME
```

The report is inventory-based; it does not substitute for an object diff. A
function’s score is meaningful only when the same target span, compiler
profile, and binary bytes are being compared.

### Interactive object diffing

Use the **objdiff GUI** for the visual per-function differ. `objdiff-cli` is
the command-line tool used for report generation, report validation, and
one-shot JSON diffs; it is not the interactive viewer.

From a checkout that contains a generated `objdiff.json` and matching base and
target object files, launch:

```sh
objdiff
```

Set the GUI project directory to that checkout, then select an object and
function from the sidebar. The GUI compares the reconstructed base object
against the retail target object and shows the instruction-level diff. This
checkout currently contains the retail image and report inventories, but not a
complete object-build configuration, so the GUI requires the corresponding
target/build outputs from a configured ARMCC build environment.

The report path is independently verified with:

```sh
python3 scripts/generate_decomp_report.py --output build/report.json
objdiff-cli report changes build/report.json build/report.json \
  --format json --output build/report-check.json
```
